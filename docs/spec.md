# Urmotiv 产品与技术规格

- 版本：0.1
- 日期：2026-07-25
- 状态：第一阶段实现基线

## 1. 目标

Urmotiv 为 USTC 算法竞赛协会命题组提供一套私有题库系统。第一阶段必须形成一条完整且安全的工作流：

1. 用户通过邮箱或 USTC 统一身份认证登录；
2. 有投题权限的用户创建草稿，用 Markdown 编写基础题面和基础题解；
3. 用户提交题目，系统冻结需要稳定审阅的基础题面和基础题解两个字段并进入待审核状态；题目名称可以在待审核与通过状态中继续编辑；
4. 审题人提交结构化意见，审核规则据此给出通过或不通过结果；
5. 有权限的成员继续补充完整题面、样例、题解、附件、测试数据和评测配置；
6. 组长从合适且未发生泄题风险的题目中组题；
7. 管理员把完整题目导入或导出为 Urmotiv、Hydro 等 OJ 的题目包；
8. 原题检索和 AI 审核作为独立服务接入，不把模型密钥或大规模题库放进 Urmotiv。

系统不执行参赛者代码，不承担沙箱、编译器和评测机职责。

## 2. 解释用语

本文尽量使用常见表达。下面这些技术名词只保留必要部分：

- **角色**：一组预设权限，例如“投稿人”“审题人”“组长”。角色用于快速分配，不代替最终权限检查。
- **明确拒绝**：单独写明某项操作不允许。只要存在明确拒绝，即使另一个角色允许，最终也不允许。
- **作用范围**：权限适用的对象，例如全部题目、自己的题目或指定的一道题。
- **插件钩子**：程序在固定时刻调用插件的入口。例如提交题目前先询问插件是否允许继续。
- **格式适配器**：在 Urmotiv 内部题目格式与某个 OJ 格式之间转换的代码。每个 OJ 使用独立适配器。
- **对象存储**：专门保存压缩包、测试数据和附件的文件服务。数据库只保存文件信息和位置。
- **后台任务**：耗时操作先排队执行，页面显示进度，用户不需要一直保持请求连接。

不得在界面中出现未经解释的内部名词。

## 3. 用户与身份

### 3.1 内部账号

- 每个用户有不可修改的内部编号。初始 `0` 号 `root` 是不可登录的内部初始化授权者，固定不绑定密码、
  邮箱、CAS 身份、会话或 API 令牌；首位真人管理员必须由服务器真实终端另建。
- 昵称可重复且可修改，不能用于识别身份或授权。
- 学号用于搜索、历史数据匹配和预创建账号，但不作为数据库主键。
- 同一人可能先后拥有多个学号，因此账号可绑定多个“用户标识”；标识记录类型、值、来源和有效期。
- 账号可填写可选的 QQ 号码和选择头像来源（不使用、QQ 头像或已上传头像）。QQ 号码仅本人可见，
  不进入公开接口、题目包或历史迁移；头像下载走权限检查，QQ 头像由服务端从固定 CDN 获取，
  不把 QQ 号暴露给浏览器。

### 3.2 邮箱登录

- 邮箱注册可由系统设置开启或关闭。
- 普通邮箱注册必须有已验证邮箱和密码。
- 一个账号可绑定多个邮箱，一个标准化后的邮箱只能属于一个账号。
- 普通账号至少保留一个邮箱。OAuth2 首次登录必须取得合法邮箱；经典 CAS 兼容模式仍允许身份源未返回邮箱的账号暂时没有邮箱。
- 密码使用 Argon2id 保存。修改密码、邮箱或权限后可撤销现有会话。
- 生产环境默认所有会话和认证浏览器绑定 Cookie 使用 `Secure`。仅当 `URMOTIV_ALLOW_LOOPBACK_INSECURE_COOKIES=true` 且 `URMOTIV_WEB_ORIGIN` 的所有配置 origin 都是 HTTP 的 `localhost`、`127.0.0.1` 或 `[::1]` 时，才允许 SSH 本机回环测试使用非 `Secure` Cookie；非回环 HTTP origin 或非回环 opt-in 会阻止服务启动。

### 3.3 USTC 统一身份认证

- 主要接入方式是 USTC CAS 提供的 OAuth2 授权码流程：浏览器只取得短期授权码，API 使用服务器私有的
  `client_id`、`client_secret` 和固定回调地址向令牌端点换取访问令牌，再向资料端点读取身份。
- `client_id`、`client_secret`、公开站点来源、授权/令牌/资料端点和回调地址由服务器管理员在私有环境文件中
  手工配置。`client_secret` 不写数据库、不进入管理接口、日志或审计，也不会返回给浏览器。
- 外部身份以“认证来源 + 稳定编号”唯一识别；稳定编号优先取资料中的 `gid`，缺失时取顶层 `id`。
  首次登录把 `zjhm` 写为用户名、`name` 写为真实姓名、`email` 写为已验证主邮箱。缺少稳定编号或这些建档字段时失败关闭。
- 后续登录只复用相同来源和稳定编号对应的账号，不覆盖用户昵称；服务端更新来源权威的真实姓名。
  学工号、主邮箱或同一稳定编号的用户名与现有绑定冲突时固定拒绝，不自动创建、合并或改绑账号。
- OAuth2 `state` 使用独立 HMAC 密钥签名，包含期限、一次性随机值、安全返回路径和发起浏览器的绑定摘要。
  原始浏览器绑定值只放入 `HttpOnly`、`Secure`、`SameSite=Lax`、`Path=/` 且不设置 `Domain` 的 `__Host-` Cookie；回环 HTTP opt-in 时仍保留这些属性（`Secure` 除外），并使用不带 `__Host-` 前缀的同源 Cookie 名称。
  回调先校验签名、期限、返回路径和浏览器绑定，再一次性消费状态，最后换码取资料；重放、缺 Cookie、错误 Cookie、
  非法授权码、上游失败或资料缺项统一返回未登录响应，不泄露原因，也不把授权码、令牌或资料写入日志。
- 开始和回调响应禁止缓存并使用 `Referrer-Policy: no-referrer`；成功后只清除当前流程的绑定 Cookie，
  多个标签页互不覆盖。返回地址只能是本站绝对路径，不能跳到其他站点。
- 经典 CAS 票据协议保留为显式兼容模式，继续使用原有独立状态版本、Cookie 前缀和配置；它不能替代 OAuth2，
  也不能复用 OAuth2 的状态密钥。
- 统一身份认证创建的账号默认没有密码，不能直接使用邮箱密码登录；用户完成设置密码后才可开启。

### 3.4 机器人账号

- 机器人通过可撤销、可过期、只显示一次的 API 令牌登录。数据库只保存令牌摘要。
- 令牌有独立权限范围、最近使用时间和可选的来源地址限制。
- 无论角色如何配置，机器人都不能删除题目或用户、模拟其他用户、修改权限、管理系统、读取密钥或创建更高权限令牌。

## 4. 权限原则

详细权限表和计算顺序见 [permissions.md](permissions.md)。核心原则如下：

- 每个接口先确认账号仍可登录，再确认账号类型的固定限制，然后计算明确拒绝和允许。
- 明确拒绝永远优先；权限不足时，插件不能把结果改成允许。
- 题目列表和数据库查询先按权限缩小范围，不能先取出全部数据再在页面过滤。
- 无权查看一道题时返回与“题目不存在”相同的结果，避免泄露题号、标题和存在性。
- 附件、图片、测试数据、导出包和后台任务结果都按题目重新检查权限，不能依赖不可猜测的网址。
- 权限、状态、身份、下载、导入、导出和插件管理操作写入不可由普通管理员修改的审计记录。

默认角色只用于方便分配：

- 投稿人：投题，查看和编辑自己的题目；默认不能批量导入、导出比赛或查看他人题目。
- 审题人：查看分配或全部待审题目，提交审题意见；不自动拥有最终改状态权限。
- 命题组成员：在审题人基础上可组题和补充被授权题目的完整资料。
- 组长：拥有最终状态、组题、导入导出、标签和成员管理能力。
- 系统管理员：管理运行配置、插件和账号，但可按实际需要不授予最终审题决定权。
- root：只作为数据库初始化授权者，不能登录；真人系统管理员使用独立账号。

## 5. 题目模型

### 5.1 类型与字段

题目类型为传统题、交互题、提交答案题。每道题有稳定的内部编号和以下信息：

| 分区 | 字段 | 初次提交必填 | 说明 |
| --- | --- | --- | --- |
| 概要 | 题目名称 | 是 | 可在待审与通过状态中继续编辑 |
| 概要 | 题目类型 | 是 | 决定数据配置界面 |
| 概要 | 知识点 | 是 | 从管理员维护的两层目录多选，详细规则见 [tag-taxonomy.md](tag-taxonomy.md) |
| 概要 | CF 难度 | 否 | 800 至 3500，整百；审核后可聚合 |
| 概要 | 思维难度、代码难度 | 否 | 使用明确等级标准，见后续实验规范 |
| 审核内容 | 基础题面 | 是 | Markdown；待审与通过时冻结 |
| 审核内容 | 基础题解 | 是 | Markdown；待审与通过时冻结 |
| 完整题面 | 背景、描述、输入、输出、数据范围 | 否 | Markdown，可在审核后继续完善 |
| 样例 | 输入、输出、解释 | 否 | 可有多组，解释为 Markdown |
| 完整题解 | 正式题解、提示、标准程序 | 否 | 分别保存，受更严格权限保护 |
| 评测资料 | 测试数据、限制、子任务、计分方式 | 否 | 组题和导出前完成 |
| 程序 | checker/SPJ、interactor、评分器 | 否 | 根据题型显示 |
| 文件 | 题面图片、公开附件、内部附件 | 否 | 公开范围分别标记 |

题目内容保留修订记录。修订记录用于审计和恢复，不允许普通用户绕过冻结规则编辑旧版本。

### 5.2 状态

状态只有四种：

- `draft`：草稿，作者可编辑全部字段并提交；
- `pending_review`：待审核，基础题面、基础题解冻结，题目名称和其他字段仍可补充；
- `approved`：审核通过，基础题面、基础题解继续冻结，题目名称和其他资料可补充；
- `rejected`：审核不通过，恢复全部字段编辑，可修改后重新提交。

允许的状态变化：

| 当前状态 | 操作 | 目标状态 | 默认操作者 |
| --- | --- | --- | --- |
| 草稿 | 提交 | 待审核 | 作者 |
| 待审核 | 审核规则判定通过 | 审核通过 | 规则或有最终决定权的人 |
| 待审核 | 审核规则判定不通过 | 审核不通过 | 规则或有最终决定权的人 |
| 待审核 | 撤回 | 草稿 | 作者或组长 |
| 审核通过 | 撤回修改 | 草稿 | 作者在题目尚未锁定到比赛时；否则需组长 |
| 审核不通过 | 修改 | 审核不通过 | 作者，保持状态 |
| 审核不通过 | 重新提交 | 待审核 | 作者 |

每次提交新建一个审核轮次。旧轮次意见保留，但不参与新轮次自动判定。

### 5.3 审核意见

审题人每轮可提交或更新一份结构化意见，包含：

- 必填：通过、不通过或需要修改；
- 必填：CF 整百难度、题目质量、原创性、思维难度、代码难度、主要改进点；
- 可选：知识点修正、公开评论、仅审题人可见备注；
- 来源：人工、Anklang 原题检索、Fermata 机器人或其他插件。

原创性使用独立的 `originalityLevel` 字段，取 1 至 5 的整数，不能用题目质量代替：

| 等级 | 含义 |
| --- | --- |
| 1 | 在当前已检查资料中，核心想法与已知题目高度重合，需要进一步核对是否适合使用 |
| 2 | 主要使用常见做法，区别或新增部分较少 |
| 3 | 使用常见方法，但组合、模型或题目设定有明确区别 |
| 4 | 核心观察、模型或构造在当前已检查范围内有明显新意 |
| 5 | 核心想法在当前已检查范围内表现出很高的新颖程度 |

这个等级只是审题人根据当时可见资料作出的评价，不是对全世界题库的完整查重，也不等同于认定题目抄袭或没有抄袭。
Anklang 等检索结果可以作为依据，但不能自动替代审题人的这项评价。新增或更新意见时必须填写该字段；数据库迁移前已经
存在的历史意见可以为 `null`，页面显示“历史意见未填写”，不能用题目质量或固定默认值伪造回填。

能查看题目的人可以查看当前轮次的公开评价字段；仅审题人可见备注仍按单独权限隐藏。
每名审题人每轮只能修改自己提交的那一份意见，不能替别人创建或修改意见。保存修改后服务端会重新执行
本轮审核规则，因此题目可能立即通过或不通过；轮次结束后，已有意见只读。

默认审核规则可配置“需要多少个通过”和“多少个不通过会阻止通过”。建议初始值为两个通过、零个阻止性不通过，
组长保留最终决定权。规则只读取当前轮次、仍有审核权限的有效意见。

只有题目仍处于 `approved`，且当前审核轮次已经以 `approved` 关闭时，才能生成和写回本轮建议。已经撤回、驳回、仍在审核、
进入新一轮或只是历史上曾通过的轮次都不能写回。服务端只使用轮次关闭时冻结的 `countedOpinionIds` 对应意见；编号重复、
缺失或指向其他轮次时整份建议不可用，不能按仍能找到的部分意见继续计算；列表为空时也不生成建议。人工终审的
`usedOpinionIds` 可以为空，因此不能用它替代 `countedOpinionIds`。

建议值按以下固定规则计算：

- CF 难度取有效值的算术平均数，再四舍五入到最近的整百；恰好在两个整百中间时向上取整；
- 思维难度和代码难度分别排序后取中位数；意见数为偶数时，先取中间两项的算术平均数，再四舍五入到 1 至 5 的整数，
  恰好为半级时向上取整；
- 知识点取去重后的并集；确认写回时仍要检查每个知识点当前存在且可用；
- 题目质量和原创性只作为审核评价与只读汇总展示，当前题目模型没有对应的正式字段，不能写回题目。

所有能查看题目的人都可以查看由公开评价字段得到的建议以及“当前值与建议值”的对照；私密备注不参与计算，也不能进入
建议或审计。组长必须明确选择要应用的字段后再确认，页面默认不选择任何字段，不能无提示覆盖作者内容。

确认写回使用专门的 `POST /api/v1/problems/:problemId/review-suggestions/apply` 接口，不能借普通题目更新接口提交所谓的
聚合结果。请求只包含 `expectedRound`、`expectedRevision` 和去重后的字段名列表；字段名只能是
`codeforcesDifficulty`、`thinkingLevel`、`codingLevel`、`tagIds`。服务端在锁定题目的同一数据库事务中重新读取冻结意见、
重新计算所选值、创建题目修订并写审计记录，不能信任浏览器显示或提交的建议数值。审计只记录审核轮次、修改前后修订号、
所选字段名和使用的意见数量，不记录题目内容、评价正文、私密备注、知识点列表或聚合后的具体值；审计失败时题目修订也必须
回滚。

### 5.4 知识点目录

知识点采用固定的“分类—标签”两层目录，分类用于折叠展示，题目可以选择一至三十枚启用的标签。普通用户不能自由输入或
自动创建标签；拥有 `tag.manage` 的真人管理员可以在后台新增和管理目录。机器人固定禁止这项权限，角色和插件不能解除。

目录、术语待确认项、Hydro 参考边界以及完整停用流程见 [知识点目录与管理规格](tag-taxonomy.md)。目录管理使用稳定编号、
单调递增的目录版本、事务和不可修改的审计。停用被使用的标签时，系统必须从所有受影响题目的当前版本中去除它并创建新修订；
题目原本只有这一枚标签时必须选择启用的替代标签。历史修订、旧审核意见和比赛固定快照保持原样并显示“已停用”，不能为方便
删除而改写历史。

外部包和历史材料中的未知标签不得静默丢弃或自动加入目录，必须在预览中完成人工映射或逐项明确忽略。历史列表中由投题者
自填的知识点只能作为私有人工映射线索，仍需独立核对后才能进入正式目录；自填难度不得进入题目候选、模型提示或 Fermata
准确性标定，也不得作为人工真值。题目难度必须使用独立人工评定或可靠公开比赛结果。

## 6. 题目访问记录与组题

- 用户打开有权限的题面时创建访问记录；页面每隔一段时间发送活动信号，切到后台后停止计时。
- 系统保存首次访问、最后访问和累计活动时长，不把打开标签页后的全部时间当作阅读时间。
- 只有拥有查看记录权限的人能看到访问者明细。
- 组题筛选可排除曾经看过题面的人将参加的比赛。比赛中记录题目版本，避免题目后续修改悄悄改变已组好的比赛。
- 组题包含比赛信息、题目顺序、分值、来源版本、预计难度、泄题风险提示与导出记录。
- 普通投稿人不能读取、导入或导出比赛内容。

## 7. 导入导出

详细格式见 [problem-package.md](problem-package.md)。这里规定产品行为：

- 题目包是完整资料，不是元数据表。能够表达题面、题解、样例、资源、测试数据、限制、子任务、计分方式、
  checker/SPJ、interactor、标准程序和附件。
- 第一阶段实现 Urmotiv 原生包和 Hydro 适配器；适配器接口允许继续加入 FPS XML、Polygon 或其他 OJ。
- 标准 OJ 包导入与历史资料迁移是两个入口。前者追求可逆转换，后者允许人工映射和 LLM 辅助，但每一题都必须预览确认。
- 导入流程为：上传、识别格式、解析预览、字段映射与冲突选择、安全校验、后台执行、逐题报告。
- 未知知识点必须在预览中映射到当前启用标签或逐项明确忽略；不得静默丢弃、模糊猜测或自动创建正式标签。
- 导出流程为：选择题目和版本、选择目标格式、选择包含内容、查看丢失信息警告、后台生成、短期下载。
- 目标格式无法表达的信息不能静默丢弃，必须列出警告；原生包往返应保持全部受支持字段和文件校验值不变。
- `.xlsx` 历史列表和 `hist_problem/` 只用于私有迁移，不进入 Git、测试快照、日志或公开示例。

## 8. 插件与外部服务

插件规则见 [plugins.md](plugins.md)。核心程序提供以下稳定入口：

- 提交前检查与提交后通知；
- 审核通过判定规则；
- 审核条目写入；
- 题目包格式适配器；
- 后台任务；
- 系统设置页面中的受控配置表单；
- 题目详情、编辑器和审核页的固定扩展位置。

Anklang 通过提交前检查或手动“原题检索”动作工作，以题目内容摘要作为缓存依据，只返回候选题、相似度、来源和候选元数据；
它是纯粹的原题检索服务，不形成是否重复或是否可参考的判定。作者和审题人可以查看结果。
candidate/推荐与复用字段是可选的：未声明时 Urmotiv 不合成拦截建议、缓存期限或“不缓存”策略，候选仍然可见。

Fermata 使用机器人 API 主动领取待审任务并提交结构化意见；Urmotiv 插件只负责配置、健康状态和任务显示。
两个服务均不能直接访问 Urmotiv 数据库。

机器人客户端的续租与完成请求必须使用调用方生成、同一次操作重试时复用的 UUID 请求标识。相同标识和相同载荷在响应
丢失后重试时返回第一次已经提交的固定结果，不重复延长租约、写审核意见或写审计；相同标识配不同载荷固定冲突。
缺少请求标识固定按无效输入拒绝；部署顺序必须先升级 Fermata 稳定发送 UUID，再部署本服务端约束。服务端在每次执行时重新检查令牌上限、
账号明确拒绝、题面可见性、审题权限、轮次和领取时的题目修订。

## 9. 前端体验

### 9.1 视觉原则

- 借鉴参考图的工作台感、清晰分区、编辑预览与数据点表格，不复制双语切换、超长单页和重复悬浮保存按钮。
- 使用白色和中性灰作为底色，深色文字，青绿色作为主操作色，另用绿色、琥珀色和红色表示状态。
- 不使用渐变、装饰光球、过大的标题或层层嵌套卡片。卡片圆角不超过 8px。
- 工具按钮使用 Lucide 图标；不熟悉的图标有悬停说明。文字命令只用于提交、保存、导入等明确动作。
- 桌面、平板和手机都不能出现文字溢出、遮挡或因动态内容改变尺寸而跳动。

### 9.2 页面结构

- 全局导航：题目、我的投稿、待审、组题、导入导出、管理；右上角头像链接到个人资料页（昵称、QQ、头像和身份标识）。
- 题目列表：按状态、类型、难度、知识点、作者、访问风险筛选与排序；服务端分页。
- 题目工作台：概要、题面、样例与约束、数据与评测、题解与资料、审核记录六个标签页。
- 知识点选择器按分类折叠并支持多选和搜索；后台设置为拥有 `tag.manage` 的真人管理员提供目录管理和删除影响预览。
- 顶部固定区只显示题号、名称、状态、保存状态和当前最重要动作。
- 审核记录采用同页侧栏或独立标签，不用遮住题面的多层弹窗。

### 9.3 Markdown 编辑器

- 支持 Markdown、代码块、表格、图片和 KaTeX 数学公式。
- 桌面默认编辑与预览并排，可切换单栏；手机用“编辑/预览”分段控件切换。
- 工具栏使用稳定尺寸的图标按钮，支持撤销、重做、标题、粗体、斜体、代码、链接、图片、表格和公式。
- 粘贴或上传图片后插入受权限保护的资源引用；未完成上传时不能提交。
- 自动保存显示“正在保存、已保存、保存失败”，失败内容保留在浏览器并可重试。

### 9.4 数据配置

- 支持 ZIP 或散文件上传，自动配对 `.in/.out`，报告缺失配对、重名、空文件和非法路径。
- 表格列为数据点、输入、输出、时间、内存、分值和子任务；支持全局默认、批量填充和多选修改。
- 子任务支持加和、最小值、最大值及目标 OJ 能表达的其他计分方式，总分与依赖关系必须校验。
- 传统题显示输入输出与 checker；交互题显示 interactor；提交答案题显示输入包与评分器。

## 10. 技术结构

采用 pnpm 工作区管理 TypeScript 代码：

```text
apps/
  web/        React 前端
  api/        HTTP API 与认证
  worker/     导入导出、文件检查和通知等后台任务
packages/
  contracts/  前后端共用的数据结构与校验
  database/   数据库结构、迁移和查询
  plugin-sdk/ 插件接口与测试工具
  ui/         通用界面组件
plugins/
  review-default/  默认审核规则
  hydro-format/    Hydro 格式适配器
```

- Web：React、Vite、React Router、TanStack Query、Markdown 编辑器、KaTeX、Lucide。
- API：Fastify，按 `/api/v1` 提供 JSON 接口并生成 OpenAPI 文档。
- 数据库：生产使用 PostgreSQL；本地轻量模式使用与 PostgreSQL 语义接近的 PGlite 文件数据库。
- Redis：生产用于任务队列、限流和短期缓存；本地轻量模式使用单进程实现。
- 文件：生产使用兼容 S3 的对象存储；本地写入 `.data/storage/`，两者通过同一接口访问。
- 数据校验：共享结构在接口入口和插件边界再次验证，不能信任浏览器或插件输入。

代码保留不依赖 Docker 的轻量开发入口，但本项目的构建、自动化测试、数据库迁移和浏览器联调统一在 `ssh ustc`
服务器进行。服务器通过 Docker Compose 运行完整环境，Web 测试端口通过 SSH 转发到本机查看。真实题目和密钥如需用于
测试，只通过 `scp` 传入服务器的非 Git 私有目录。

## 11. 安全与可靠性

- 会话使用带 `HttpOnly`、`Secure`、`SameSite` 的 Cookie，写操作校验跨站请求来源。
- 登录、令牌和导出接口限速；连续失败记录审计事件。
- 所有上传按实际内容和扩展名共同检查，限制单文件、总解压大小、文件数和嵌套层数。
- 不直接公开对象存储路径。下载先走权限检查，再返回短期有效地址或由 API 转发。
- 导入过程先写临时区，全部校验通过后在数据库事务中发布；失败不留下半道题目。
- 后台任务可重试但必须防止重复创建题目或重复提交审核。
- 插件有执行超时、错误隔离和健康状态；提交前插件失败时按配置选择“阻止提交”或“记录后继续”，默认阻止需要查重的提交。
- 审计记录包含操作者、时间、动作、对象、结果和请求编号，不保存题面正文与密钥。

## 12. 版本、部署与升级

- 使用语义化版本，例如 `0.1.0`。数据库迁移和插件接口都有单独兼容版本。
- Docker Compose 提供基础服务与可选的 Anklang、Fermata 组合配置。
- 升级脚本读取服务器已有部署配置，依次拉取指定版本、备份数据库、构建镜像、执行迁移、滚动重启和健康检查；
  失败时停止继续升级并给出恢复命令，不能猜测或覆盖启动参数。
- `.env.example` 只列字段和说明，不包含真实值。密钥通过服务器环境或密钥文件提供。

## 13. 验收标准

第一阶段完成需同时满足：

1. USTC 服务器环境可完成登录、创建草稿、Markdown 预览、提交、审核、补充数据、导出和重新导入；
2. 待审与通过状态只冻结基础题面和基础题解，题目名称可继续编辑，后端与前端行为一致；
3. 普通用户通过列表、猜题号、附件地址、后台任务和导出接口都拿不到他人题目；
4. 机器人无法调用固定禁止的操作，即使错误分配了管理员角色；
5. Urmotiv 原生包导出后重新导入不丢字段和文件，Hydro 转换有人工构造的合成夹具往返测试与丢失信息报告；
   合成夹具不能冒充真实 Hydro 导出样例，与固定上游实现互相导入的证据按
   [OJ 题目包兼容性与证据边界](oj-compatibility.md)单独验收；
6. Markdown、公式、图片、样例和数据点页面在桌面与手机截图中可读且无重叠；
7. Docker Compose 在 USTC Ubuntu 服务器启动后通过健康检查，升级脚本能保留配置并重启服务；
8. README、插件文档、接口文档和权限表与实现一致。

## 14. 暂不阻塞开发的待确认项

- CAS 实际返回的稳定身份字段名称；真实联调前由配置占位，不能据此完成最终上线验收。
- Hydro 以外第一批必须支持的 OJ。适配器接口先稳定，默认候选为 FPS XML。
- 审核通过人数、阻止性不通过人数和组长是否必须终审。第一版按可配置规则实现。
- 思维难度、代码难度与 AI 评分的最终数值标准。必须由 Fermata 的实验集校准后启用，不能先放任意公式。
