# 插件规范

需要动手写插件，见 [插件开发教程](plugin-development.md)——本文是设计规范，教程讲的是具体怎么建文件、
调用哪些真实接口、怎么把插件接进服务器。

## 1. 插件是什么

插件是随 Urmotiv 服务器一起安装、由管理员明确启用的扩展代码。它可以在程序预留的位置增加检查规则、
后台任务、格式转换或界面区域。插件不是从网络任意加载的脚本，也不能自动获得管理员权限。

插件分为两类：

- **内置插件**：随主仓库发布，例如默认审核规则和 Hydro 格式适配器；
- **受信任插件**：管理员从本地包安装，记录来源、版本和摘要，重启服务后生效。

第一阶段不运行来源不明的插件。真正隔离不可信代码需要单独进程或容器，仅靠 JavaScript 限制不足以保证安全。

## 2. 插件目录

```text
plugins/example/
  package.json
  urmotiv-plugin.json
  src/
    server.ts
    worker.ts
    web.tsx
  migrations/
  README.md
```

清单文件描述插件，不执行代码：

```json
{
  "id": "org.example.review-rule",
  "name": "示例审核规则",
  "version": "1.0.0",
  "apiVersion": "1",
  "serverEntry": "dist/server.js",
  "workerEntry": "dist/worker.js",
  "webEntry": "dist/web.js",
  "permissions": ["org.example.review-rule.configure"],
  "settingsSchema": "settings.schema.json"
}
```

插件编号使用域名倒序或组织前缀，避免两个插件同名。界面仍显示易懂的中文名称。

## 3. 启动过程

1. 核心程序读取已安装清单，检查编号、摘要、版本和主程序接口版本。
2. 数据库迁移只在管理员确认的升级步骤执行，不在普通请求中自动执行。
3. 插件收到受限的服务集合，用它注册钩子、任务、格式适配器和界面扩展。
4. 注册完成后锁定注册表；请求过程中不能偷偷替换其他插件的函数。
5. 启动失败的插件标记为不可用，记录不含密钥的错误。核心插件失败则健康检查不通过。

插件不能直接拿到应用的数据库超级用户密码、Cookie 密钥、CAS 密钥或其他插件设置。

## 4. 服务端入口

### 4.1 提交前检查

`problem.beforeSubmit` 在核心权限、字段和状态检查通过后、数据库改为待审核前运行：

```ts
type BeforeSubmitResult =
  | { decision: "continue"; reviewItems?: ReviewItemInput[] }
  | { decision: "block"; code: string; message: string; details?: unknown };
```

- 多个检查按管理员配置的顺序运行；任何 `block` 都会阻止提交。
- 插件只能返回审核条目或阻止原因，不能直接修改所有者、权限、状态和冻结字段。
- 每个检查有超时和取消信号。超时如何处理由该检查设置决定，涉及必须完成的原题检索时默认阻止提交。
- 同一内容摘要再次提交时，插件可返回可复用结果；是否可复用由插件和核心保留期共同决定。

### 4.2 提交后通知

`problem.afterSubmit` 在事务完成后通过后台任务调用，用于通知或后续分析。它失败不会撤销已经成功的提交，
但会显示失败状态和重试入口。

### 4.3 审核规则

插件可注册多个命名规则：

```ts
interface ReviewDecisionRule {
  id: string;
  displayName: string;
  evaluate(input: ReviewRoundSnapshot, settings: unknown): Promise<ReviewDecision>;
}
```

快照只包含当前轮次中仍有效的意见和规则声明支持的审核条目，不提供任意数据库查询。每份意见可读取结论、CF 难度、
质量、思维难度、代码难度、建议知识点编号和主要改进点，以及去重和判断来源所需的审题人编号、账号类型、来源和更新时间。
仅审题人可见备注、题目名称、题面、题解、附件和测试数据永远不进入这个快照。快照使用严格的数据结构校验并在调用前
冻结，插件不能加入未知字段或改写输入。返回值为保持待审、通过或不通过，并列出使用了哪些意见和理由。核心再次校验
意见有效性，然后在事务中改变状态。

默认插件实现“达到通过人数且没有达到阻止人数”。组长可以在系统设置选择一个规则和它的配置。
需要按质量、难度或知识点判断时，插件应为自己的门槛定义严格的设置结构，管理员再选择该命名规则并保存设置；
不能把未声明的设置或私密备注作为隐藏输入。

### 4.4 审核条目

原题检索、AI 分析和静态检查都写成独立审核条目：

- `type`：稳定类型编号；
- `source`：插件、机器人或人工账号；
- `visibility`：作者可见、审题人可见或仅管理员可见；
- `summary`：短说明；
- `data`：经过该类型数据结构校验的内容；
- `contentHash`：对应的题目内容摘要；
- `createdAt` 和可选到期时间。

审核规则只能读取它明确声明支持的条目类型，不能把任意插件文本当作通过票。

### 4.5 格式适配器与后台任务

格式适配器遵循 [problem-package.md](problem-package.md) 的统一接口。插件可注册自己的后台任务类型，
但任务参数必须校验、可取消、可重复执行且不会重复产生数据。

## 5. 数据库使用

插件如需保存数据，必须声明独立数据库命名空间和迁移：

- 表名或数据库结构使用插件编号生成的稳定前缀；
- 通过核心提供的事务和查询接口访问，不能获得数据库管理员连接；
- 读取核心题目时使用已经做过权限和范围检查的服务，不能直接查询核心表绕过权限；
- 卸载默认保留数据，管理员可在单独确认后清理；
- 禁用插件后核心题目和审核记录仍可读，插件私有详情显示为不可用。

这满足插件保存配置和结果的需求，同时避免一个插件随意修改账号或题目状态。

## 6. 插件权限

插件可以声明自己的权限，例如“配置原题检索服务”或“查看原题候选详情”。安装时核心登记这些权限，管理员再放进角色。

插件权限遵守同一套明确拒绝优先规则。插件不能：

- 创建与核心权限同名的权限；
- 把自己的权限解释成核心权限；
- 自动给安装者或 root 以外账号授权；
- 解除机器人固定禁止项；
- 在停用或卸载时留下默认允许的未知权限。

## 7. 前端扩展

插件不能查找页面元素后随意改网页。核心提供固定扩展位置，例如：

- 题目详情的“外部分析”区域；
- 题目编辑器主操作旁的检查按钮；
- 审核页的独立审核条目；
- 系统设置中的插件配置页；
- 导入导出格式列表。

简单设置优先由 JSON Schema 生成受控表单。JSON Schema 是一份描述字段类型、必填项和限制的普通 JSON 文件，
核心据此生成输入框，并在服务端再次校验。

需要自定义交互的受信任插件可提供 React 组件，但必须：

- 使用插件开发包提供的数据和动作，不能直接读取 Cookie、全局状态或其他页面缓存；
- 只能出现在声明的扩展位置；
- 复用核心界面组件、图标和颜色变量；
- 通过主应用构建或受校验的同源模块加载，不能从第三方网址运行脚本；
- 自己做隐藏按钮之外，所有动作仍调用有权限检查的 API。

## 8. 设置与密钥

- 普通设置按插件数据结构保存，变更写审计记录。
- 修改被拒绝或保存失败时，只记录操作人、插件编号和固定失败原因；不记录请求正文、设置值、密钥值或内部错误内容。
- 密钥字段单独加密保存，读取接口只返回“已配置”和末尾少量字符，永不返回完整值。
- 插件运行时按具体密钥名称申请使用，不能列出或读取其他插件密钥。
- 导出站点配置、日志和错误报告时不包含密钥。
- 配置页标明修改是否需要重启、重新处理旧结果或使缓存失效。
- 数据库已经保存插件密钥时，服务器必须带原来的加密配置启动；缺少配置时停止启动，不能把读取失败当成“没有设置密钥”。

## 9. Anklang 接入

Urmotiv 内的 Anklang 插件只做以下工作：

1. 保存服务地址、认证信息和超时设置；
2. 在手动检查或提交前发送必要的题目内容和内容摘要；
3. 校验返回的候选题、相似度、来源、建议布尔值和文字说明；
4. 把结果保存为审核条目并按摘要缓存；
5. 显示服务健康状态和任务错误。

候选题正文和 Anklang 的完整公开题库不复制进 Urmotiv 数据库。LLM 建议只是审核信息，不能绕过人工或选定审核规则。

## 10. Fermata 接入

Fermata 不是服务器内插件。它使用机器人令牌调用版本化 API：

- 领取有权查看且尚未处理的待审题目；
- 读取允许范围内的题面、题解和已有审核条目；
- 提交结构化审核意见和分析版本；
- 汇报任务状态、模型配置名称和实验版本，不上传模型密钥；
- 定期续租任务，超时后任务可由其他工作进程领取。

Urmotiv 的 Fermata 管理插件提供开关、队列、健康状态和可公开设置，不把 Fermata 变成站内任意代码执行器。
当前内置定义已支持加密保存管理令牌，但 API 尚未调用 Fermata 的状态、设置和立即检查接口；管理页面接线时必须
区分“配置已保存”和“服务已连通”。

## 11. 插件测试要求

每个插件至少提供：

- 清单和设置数据结构测试；
- 主程序接口版本兼容测试；
- 权限拒绝、机器人固定限制和字段冻结测试；
- 超时、取消、返回畸形数据和外部服务不可用测试；
- 数据库迁移升级与回退说明；
- 若有界面，桌面和手机截图检查；
- 若为格式适配器，按题目包规范提供安全与往返测试；
- README，使用普通语言说明作用、数据流向、权限、设置、失败影响和卸载结果。

## 12. 插件如何“中断”原操作

提交等关键操作被拆成三个阶段：核心检查、提交前插件、数据库提交。插件并不是强行暂停任意代码，而是在核心明确预留的
第二阶段返回“继续”或“阻止”。只有全部必需检查返回继续，核心才在一次数据库事务中改变状态。

页面扩展也不是修改现有网页源代码。核心在已知位置渲染插件登记的组件，并只给它必要的数据和动作。这种方式能控制权限、
失败范围和升级兼容性；允许插件随意改页面或数据库虽然看似自由，但一个错误就可能泄露所有私题，因此不采用。
